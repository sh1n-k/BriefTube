# BriefTube 워커 아키텍처

> 5개의 비동기 워커가 YouTube 영상 수집 → 자막 추출 → LLM 기사화 → Telegram 알림 + 영상 다운로드 파이프라인을 구성한다.

---

### 워커 간 통신 채널

| 통신 방식 | 발신 | 수신 | 용도 |
|-----------|------|------|------|
| `videos` 테이블 상태 전이 | Poller → Transcript → LLM | 각 다음 단계 워커 | 파이프라인 체이닝 |
| `notification_queue` (asyncio.Queue) | LLM Worker | Notifier | 기사 완성 알림 |

| `app_settings` KV 테이블 | Transcript Worker | Transcript Worker (재시작 시) | Guard 상태 영속화 |
| `system_alerts` 테이블 | RSS Poller | 웹 UI (토스트) | 채널 404 등 운영 이벤트 |

## 2. 라이프사이클

`main.py`의 lifespan 컨텍스트 매니저에서 5개 워커를 동시에 생성하고, 앱 종료 시 일괄 취소한다.

```python
# main.py (lifespan)
tasks = [
    asyncio.create_task(run_rss_poller(runtime),        name="rss_poller"),
    asyncio.create_task(run_download_worker(runtime),    name="download_worker"),
    asyncio.create_task(run_transcript_fetcher(runtime), name="transcript_fetcher"),
    asyncio.create_task(run_llm_queue_worker(runtime),   name="llm_queue_worker"),
    asyncio.create_task(run_telegram_notifier(runtime),  name="telegram_notifier"),
]

# 종료 시
for t in tasks:
    t.cancel()
await asyncio.gather(*tasks, return_exceptions=True)
await http_client.aclose()
await db.close()
```

### 공유 상태 (AppState)

모든 워커는 `AppState` 인스턴스를 통해 공유 자원에 접근한다.

```
AppState

└── rss_cache           # dict (ETag/Last-Modified)
```

## 3. 워커별 상세 흐름

### 3.1 RSS Poller (`poller.py`)

> **쉬운 설명**: 구독한 YouTube 채널들의 "새 영상 목록"을 주기적으로 확인하는 워커다.
> 마치 우체부가 정해진 시간마다 우편함을 확인하듯, 15분마다 각 채널의 RSS 피드를 방문해서 새 영상이 올라왔는지 살펴본다.
> 새 영상을 발견하면 DB에 등록해서 다음 워커(Transcript Worker)가 처리할 수 있게 한다.
> 만약 채널이 삭제되어 404 에러가 나면, 자동으로 채널을 비활성화하고 관리자에게 알림을 보낸다.

#### 핵심 동작

| 항목 | 값 | 설명 |
|------|-----|------|
| 폴링 간격 | `polling_interval_minutes` (기본 15분) | 최소 60초 보장 |
| Watermark | `channels.last_seen_published_at` | 채널별로 마지막 확인 시점 기록 |
| Lookback | `rss_bootstrap_lookback_days` (기본 60일) | 신규 채널 첫 폴링 시 과거 범위 |
| 즉시 트리거 | `poll_now_event` | API에서 설정하면 대기 중단, 즉시 폴링 |
| 캐시 | `rss_cache` (ETag, Last-Modified) | 304 응답으로 불필요한 처리 방지 |
| 404 처리 | 채널 자동 비활성화 | `system_alerts`에 알림 생성 |

#### DB 상호작용

- **읽기**: `channels` (is_active=1), `app_settings` (rss_bootstrap_lookback_days)
- **쓰기**: `videos` (INSERT, pipeline_status='transcript_pending'), `channels` (watermark 갱신), `system_alerts` (404 시 INSERT)

### 3.2 Transcript Worker (`transcript_worker.py`)

> **쉬운 설명**: YouTube 영상의 자막(대본)을 가져오는 워커다.
> RSS Poller가 새 영상을 등록하면, 이 워커가 YouTube에서 자막 텍스트를 다운로드한다.
> 하지만 YouTube에 너무 빠르게 요청하면 차단당할 수 있다.
> 그래서 이 워커에는 **세 가지 보호 장치**가 내장되어 있다:
>
> 1. **서킷 브레이커**: 전기 누전 시 자동으로 차단되는 두꺼비집(차단기)과 같다. YouTube가 차단(429/403)을 걸면 자동으로 "열림(OPEN)" 상태가 되어 요청을 멈추고, 쿨다운이 끝나면 조심스럽게 1건만 시도해보고(HALF_OPEN), 성공하면 다시 정상(CLOSED)으로 돌아간다.
> 2. **적응형 속도 조절**: 차를 운전할 때 빨간불이 많으면 속도를 줄이고, 파란불이 계속되면 속도를 올리는 것과 같다. 에러가 나면 요청 간격을 늘리고(factor↑), 성공이 쌓이면 간격을 줄인다(factor↓).
> 3. **채널별 쿨다운**: 같은 가게에 너무 자주 방문하면 의심받는 것과 같다. 같은 YouTube 채널에 연달아 요청하지 않도록 최소 3분(180초) 간격을 둔다.
>
> 또한, **워커 Lease(임대)**로 여러 인스턴스가 동시에 실행되더라도 한 번에 하나만 작업하도록 보장한다.

#### 서킷 브레이커 (Circuit Breaker)

서킷 브레이커는 전기 회로의 두꺼비집처럼 동작한다. YouTube가 요청을 차단하면 자동으로 모든 요청을 멈추고, 시간이 지난 후 조심스럽게 다시 시도한다.

3가지 상태가 있다:

```
  ┌───────────────────────────────────────────────────────────────┐
  │                                                               │
  │   ┌──────────┐   429/403 에러 발생    ┌──────────┐            │
  │   │ CLOSED   │ ──────────────────────▶│  OPEN    │            │
  │   │ (닫힘)    │                        │  (열림)   │            │
  │   │          │                        │          │            │
  │   │ 정상 운영 │                        │ 모든 요청 │            │
  │   │ 요청 허용 │                        │ 차단     │            │
  │   └──────────┘                        │ 쿨다운   │            │
  │        ▲                              │ 타이머   │            │
  │        │                              └─────┬────┘            │
  │        │                                    │                 │
  │        │  probe 성공                 쿨다운 만료│                │
  │        │  (시험 요청 통과)                     │                │
  │        │                              ┌─────▼────┐            │
  │        │                              │HALF_OPEN │            │
  │        └──────────────────────────────│ (반개방)  │            │
  │                                       │          │            │
  │          probe 실패                    │ 1건만    │            │
  │          (시험 요청도 차단됨)           │ 시험 요청│            │
  │                          ┌────────────│          │            │
  │                          │            └──────────┘            │
  │                          ▼                                    │
  │                   다시 OPEN 상태로                              │
  │                   (쿨다운 재시작)                               │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘
```

| 상태 | 의미 | 동작 |
|------|------|------|
| **CLOSED** (닫힘) | 정상 | 요청을 자유롭게 보낸다 |
| **OPEN** (열림) | 차단 감지 | 모든 요청을 멈추고 쿨다운 타이머가 끝날 때까지 대기한다 |
| **HALF_OPEN** (반개방) | 시험 단계 | 딱 1건만 시험 요청을 보내본다. 성공하면 CLOSED로 복귀, 실패하면 다시 OPEN |

비유하면:
- **CLOSED** = 가게 문이 열려 있어서 손님(요청)이 자유롭게 들어간다
- **OPEN** = 가게 주인이 화나서 문을 잠갔다. 일정 시간이 지날 때까지 기다린다
- **HALF_OPEN** = 시간이 좀 지나서 문을 살짝 열고 한 명만 들여보내 본다. 괜찮으면 문을 다시 연다

#### 적응형 속도 조절 (Adaptive Factor)

`adaptive_factor`는 요청 간격을 조절하는 "속도 배율"이다.

```
실제 요청 간격 = 기본 간격(15초) × adaptive_factor × (1 ± 지터)
```

- **정상 시**: factor = 1.0 → 간격 ≈ 15초
- **에러 발생 시**: factor가 커진다 → 간격이 늘어난다 (느려진다)
- **연속 성공 시**: factor가 줄어든다 → 간격이 줄어든다 (빨라진다)

##### 악화 (에러 발생 시 factor 증가)

| 에러 종류 | factor 변화 | 예시 |
|-----------|------------|------|
| 하드 쓰로틀 (429/403) | factor × 2.0 | 1.0 → 2.0 → 4.0 → 8.0(상한) |
| 일반 에러 (타임아웃 등) | factor × 1.25 | 1.0 → 1.25 → 1.56 → 1.95 |

factor의 상한은 `transcript_adaptive_max_factor` (기본 8.0)이다.

##### 복구 (연속 성공 시 factor 감소)

5회 연속 성공할 때마다 factor에 "감쇠율(decay rate)"을 곱해서 줄인다.
단, **감쇠율은 현재 factor 크기에 따라 달라진다**:

| 현재 factor 수준 | 감쇠율 | 의미 |
|-----------------|--------|------|
| factor ≥ max/2 (≥ 4.0) | × 0.5 | **공격적 복구**: 심하게 느려진 상태이므로 빠르게 회복 |
| factor ≥ max/4 (≥ 2.0) | × 0.65 | **중간 복구**: 적당히 회복 |
| factor < max/4 (< 2.0) | × 0.8 | **조심스러운 복구**: 거의 정상이므로 천천히 회복 |

비유하면: 고속도로에서 사고로 많이 감속했을 때(factor가 높을 때)는 빠르게 속도를 올리고, 거의 정상 속도에 가까울 때(factor가 낮을 때)는 조심스럽게 올리는 것과 같다.

##### 수치 시뮬레이션: 악화 경로 (연속 429/403)

| 발생 횟수 | adaptive_factor | 요청 간격 (기본 15s) | 서킷 브레이커 쿨다운 |
|-----------|-----------------|---------------------|---------------------|
| 초기 | 1.0 | ~15초 | - |
| 1회 | 2.0 | ~30초 | 5분 (300s) |
| 2회 | 4.0 | ~60초 | 10분 (600s) |
| 3회 | 8.0 (상한) | ~120초 | 20분 (1200s) |
| 4회+ | 8.0 (고정) | ~120초 | 60분 (3600s, 상한) |

##### 수치 시뮬레이션: 복구 경로 (factor=8.0에서 연속 성공)

| 복구 라운드 | 연속 성공 | 감쇠율 | adaptive_factor | 요청 간격 |
|------------|----------|--------|-----------------|----------|
| 시작 | 0 | - | 8.0 | ~120초 |
| 1차 | 5회 | ×0.5 (≥4.0이므로) | 4.0 | ~60초 |
| 2차 | 10회 | ×0.5 (≥4.0이므로) | 2.0 | ~30초 |
| 3차 | 15회 | ×0.65 (≥2.0이므로) | 1.3 | ~20초 |
| 4차 | 20회 | ×0.8 (<2.0이므로) | 1.04 | ~16초 |
| 5차 | 25회 | ×0.8 | 1.0 (하한) | ~15초 |

> 모든 간격에는 ±30% 지터가 적용되어 요청 타이밍이 랜덤하게 분산된다.

#### 채널별 쿨다운

같은 YouTube 채널에 연달아 요청하면 차단 위험이 높아진다. 그래서 두 가지 메커니즘으로 채널 요청을 분산한다.

##### 1) 일반 채널 간격 (`channel_min_interval_seconds`, 기본 180초)

마지막으로 요청한 채널과 같은 채널의 영상이 다음 후보인 경우, 해당 채널을 `avoid_channel_id`로 지정하여 다른 채널의 영상을 우선 처리한다.

```
마지막 요청: 채널 A (10:00:00)
다음 후보 : 채널 A 영상 → 3분 이내이므로 건너뜀
           채널 B 영상 → 다른 채널이므로 처리!
```

##### 2) 하드 쓰로틀 시 채널 쿨다운 (`channel_hard_cooldown_seconds`, 기본 900초)

429/403 에러가 발생한 채널에 대해, 해당 채널의 **다른 대기 영상들도** 재시도 시각을 15분 뒤로 미룬다 (`defer_channel_transcript_retries`). 차단된 채널에 계속 요청하는 것을 방지한다.

```
채널 A의 영상 X → 429 에러 발생!
→ 영상 X: 재시도 스케줄 등록 (지수 백오프)
→ 채널 A의 영상 Y, Z: transcript_next_attempt_at을 15분 뒤로 일괄 연기
```

#### 워커 Lease (임대)

여러 서버 인스턴스가 같은 DB를 공유할 때, Transcript Worker가 동시에 여러 개 실행되면 같은 영상을 중복 처리하거나 YouTube 차단을 가속시킬 수 있다.

이를 방지하기 위해 **Lease(임대)** 방식을 사용한다:

```
워커 A                        DB (app_settings)                    워커 B
──────                        ────────────────                     ──────
  │                                                                  │
  │── acquire_lease ──────▶  owner=A, expires=now+45s               │
  │   (성공! 작업 시작)                                              │
  │                                                                  │
  │                                                    acquire_lease─┤
  │                                              (실패! A가 보유 중) ─┤
  │                                                     5초 대기 후  │
  │                                                     재시도       │
  │── renew_lease ────────▶  expires=now+45s (연장)                  │
  │   (TTL의 1/3마다 갱신)                                           │
  │                                                                  │
  │── release_lease ──────▶  owner=null (해제)                       │
  │   (워커 종료 시)                                                 │
  │                                                    acquire_lease─┤
  │                                              (성공! B가 인수)   ─┤
```

| 항목 | 값 | 설명 |
|------|-----|------|
| owner_id | `transcript-{pid}-{uuid}` | 워커 인스턴스 고유 식별자 |
| TTL | 45초 (또는 fetch_timeout + 10초 중 큰 값) | Lease 유효 시간 |
| 갱신 주기 | TTL / 3 (≈15초) | 만료 전 자동 연장 |
| 비정상 종료 시 | TTL 만료 후 다른 워커가 인수 | 데드락 없음 |

---

#### 오류 4단계 분류

자막 다운로드 실패 시, 에러를 4가지 카테고리로 나눠서 각각 다르게 대응한다.

| # | 분류 | 판정 조건 | Guard 영향 | 재시도 |
|---|------|----------|-----------|--------|
| ① | **자막 없음** (NO_SUBTITLE) | `NoTranscriptFound`, `TranscriptsDisabled` 예외 | factor 변화 없음 (정상 응답 취급). 연속 성공 카운트 증가 | 재시도 없음. `no_subtitle` 확정 |
| ② | **하드 쓰로틀** (HARD_THROTTLE) | `RequestBlocked`, `IpBlocked` 예외, 또는 HTTP 429/403, 또는 메시지에 "forbidden", "too many requests", "rate limit", "quota", "captcha", "unusual traffic" 포함 | factor ×2, 서킷 브레이커 OPEN, 채널 쿨다운 발동 | 지수 백오프로 재시도. 최대 8회 |
| ③ | **재시도 가능** (RETRYABLE_TRANSIENT) | `asyncio.TimeoutError`, `YouTubeRequestFailed`, `YouTubeDataUnparsable`, `CouldNotRetrieveTranscript`, 기타 미분류 예외 | factor ×1.25 | 지수 백오프로 재시도. 최대 8회 |
| ④ | **재시도 불가** (NON_RETRYABLE_FAILURE) | `InvalidVideoId`, `VideoUnavailable`, `AgeRestricted`, `VideoUnplayable` | factor ×1.25 | 재시도 없음. 즉시 `transcript_failed` 확정 |

> **①과 ④의 차이**: 둘 다 재시도하지 않지만, ①(자막 없음)은 YouTube가 정상 응답한 것이므로 "성공"으로 취급하고, ④(재시도 불가)는 에러이므로 factor를 소폭 올린다.

---

#### 자막 재시도 지수 백오프

에러 카테고리 ②(하드 쓰로틀)와 ③(재시도 가능)에서 사용한다.

```
delay = min(base × 2^retry_count, max_delay)
```

| 재시도 횟수 | 지연 시간 | 비고 |
|------------|----------|------|
| 0 | 120초 (2분) | 첫 실패 |
| 1 | 240초 (4분) | |
| 2 | 480초 (8분) | |
| 3 | 960초 (16분) | |
| 4 | 1920초 (32분) | |
| 5+ | 3600초 (1시간) | 상한 고정 |

최대 재시도 횟수: `transcript_retry_max_attempts` (기본 8회). 초과 시 `transcript_failed` 확정.

하드 쓰로틀의 경우, 재시도 지연 시간은 `max(지수 백오프, 서킷 브레이커 쿨다운, 채널 하드 쿨다운)` 중 가장 큰 값이 적용된다.

#### Guard 상태 영속화

Guard의 모든 상태는 `app_settings` KV 테이블에 문자열로 저장된다.
서버가 재시작되어도 이전 상태가 그대로 복원되므로, 재시작으로 보호 장치가 초기화되지 않는다.

저장되는 필드:

| 필드 | 타입 | 설명 |
|------|------|------|
| `adaptive_factor` | float | 현재 속도 배율 (1.0 ~ 8.0) |
| `cooldown_until` | ISO datetime | 서킷 브레이커 쿨다운 만료 시각 |
| `consecutive_hard_errors` | int | 연속 하드 쓰로틀 횟수 (쿨다운 길이 결정) |
| `consecutive_successes` | int | 연속 성공 횟수 (복구 판정용) |
| `breaker_state` | string | 서킷 브레이커 상태 (closed/open/half_open) |
| `half_open_probe_remaining` | int | 반개방 시 남은 시험 요청 수 |
| `last_channel_id` | string | 마지막 요청 채널 ID |
| `last_channel_attempt_at` | ISO datetime | 마지막 채널 요청 시각 |

#### DB 상호작용

- **읽기**: `videos` (pipeline_status='transcript_pending', transcript_next_attempt_at 조건, avoid_channel_id 분산), `app_settings` (guard 상태, worker lease)
- **쓰기**: `transcripts` (INSERT/UPDATE), `videos` (상태/재시도 갱신, 채널 일괄 연기), `app_settings` (guard 상태 저장, lease 관리)

### 3.3 LLM Worker (`llm_worker.py`)

> **쉬운 설명**: 자막 텍스트를 읽기 좋은 "뉴스 기사"로 변환하는 워커다.
> Transcript Worker가 자막을 저장하면, 이 워커가 AI(LLM)에게 "이 자막을 기사 형태로 정리해줘"라고 요청한다.
> AI가 제목·요약·본문·팩트박스·타임스탬프를 만들어 돌려주면 DB에 저장한다.
> 만약 AI 호출이 실패하면 최대 3번까지 자동 재시도하고, 3번 다 실패하면 "사람이 확인 필요" 상태로 표시한다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   비활성화
     ┌───▶│ 워커 활성화?  │─────────▶ 5초 대기 후 재확인
     │    └──────┬───────┘
     │           │ 활성화
     │           ▼
     │    ┌──────────────────┐   없음
     │    │ LLM 후보 조회    │─────────▶ 5초 대기 ──┐
     │    │ (pipeline_status │                      │
     │    │  IN ('llm_      │                      │
     │    │  pending',      │                      │
     │    │  'llm_failed')) │                      │
     │    └──────┬───────────┘                      │
     │           │ 있음                              │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ pipeline_status  │                      │
     │    │ = 'llm_         │                      │
     │    │   processing'   │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ LLM restructure  │                      │
     │    │ (title, lead,    │                      │
     │    │  body, fact_box, │                      │
     │    │  timestamps)     │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │     성공?        │                      │
     │    └──┬──────────┬───┘                      │
     │       │ YES      │ NO                        │
     │       ▼          ▼                           │
     │  ┌─────────┐ ┌───────────────┐              │
     │  │기사 저장 │ │ retry_count   │              │
     │  │pipeline_ │ │ < 3?          │              │
     │  │status=  │ │  YES →        │              │
     │  │ 'done'  │ │   llm_failed  │              │
     │  │         │ │  NO  →        │              │
     │  │알림 큐에│ │   manual_     │              │
     │  │추가     │ │   review      │              │
     │  └────┬────┘ └───────┬───────┘              │
     │       │              │                       │
     └───────┴──────────────┴───────────────────────┘
```

#### 상태 전이

```
transcript_pending ──▶ llm_pending ──▶ llm_processing ──▶ done           (성공)
                                                     └──▶ llm_failed     (실패, retry_count < 3)
llm_failed  ──▶ llm_processing ──▶ done                                  (재시도 성공)
                               └──▶ llm_failed                           (재실패, retry_count < 3)
                               └──▶ manual_review                        (retry_count >= 3, 최종 실패)
```

#### LLM 출력 구조

```json
{
  "title":      "기사 제목",
  "lead":       "리드 문단 (요약)",
  "body":       "본문",
  "fact_box":   "팩트박스 (선택)",
  "timestamps": "타임스탬프 (선택)"
}
```

#### DB 상호작용

- **읽기**: `videos` + `transcripts` (JOIN, 후보 조회)
- **쓰기**: `articles` (INSERT/UPDATE), `videos` (pipeline_status, retry_count)
- **큐**: 성공 시 `notification_queue.put()` → Notifier로 전달

### 3.4 Download Worker (`download_worker.py`)

> **쉬운 설명**: YouTube 영상 파일(mp4)을 컴퓨터에 저장하는 워커다.
> 사용자가 웹 UI에서 "다운로드" 버튼을 누르면, `download_jobs` 테이블에 작업이 등록된다.
> 이 워커는 등록된 작업을 하나씩 꺼내서 yt-dlp 프로그램을 실행해 영상을 다운로드한다.
> 동시에 최대 2~3개까지 병렬로 다운로드할 수 있고, 완료되면 파일 경로와 크기를 기록한다.
> 다운로드 중 에러가 나면 원인(ffmpeg 없음, 403 차단, 타임아웃 등)을 분류해서 저장한다.

| `http_429` | 요청 초과 | YouTube 다운로드 제한 |
| `timeout` | 시간 초과 | `download_timeout_seconds` 초과 |
| `output_not_found` | 파일 누락 | 프로세스 성공했으나 파일을 찾을 수 없음 |
| `exception` | 기타 예외 | 예상하지 못한 런타임 에러 |

#### DB 상호작용

- **읽기**: `download_jobs` (status='pending')
- **쓰기**: `download_jobs` (status, output_path, file_size_bytes, error_code 갱신)

### 3.5 Telegram Notifier (`notifier_worker.py`)

> **쉬운 설명**: LLM이 만든 기사를 Telegram 메신저로 알려주는 워커다.
> LLM Worker가 기사를 완성하면 "알림 대기줄"(Queue)에 넣는다.
> 이 워커는 대기줄을 지켜보다가, 기사가 도착하면 1초 정도 기다려서 여러 건을 모은 뒤
> 하나의 Telegram 메시지로 묶어서 보낸다.
> Telegram 설정(토큰, 채팅 ID)이 없으면 자동으로 대기 상태가 된다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   미설정
     ┌───▶│ TG 설정 확인  │─────────▶ 5초 대기 후 재확인
     │    │ (토큰+채팅ID) │
     │    └──────┬───────┘
     │           │ 설정됨
     │           ▼
     │    ┌──────────────┐   비활성화
     │    │ 워커 활성화?  │─────────▶ 3초 대기 후 재확인
     │    └──────┬───────┘
     │           │ 활성화
     │           ▼
     │    ┌──────────────────┐   타임아웃 (3초)
     │    │ 큐에서 아이템 대기│─────────▶ continue ──┐
     │    │ (timeout=3초)    │                      │
     │    └──────┬───────────┘                      │
     │           │ 아이템 수신                        │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 1초 대기 후       │                      │
     │    │ 추가 아이템 수집  │                      │
     │    │ (get_nowait 반복) │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 배치 메시지 포매팅│                      │
     │    │ (HTML 형식)      │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ Telegram 발송    │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 응답 확인        │                      │
     │    │ 실패 시 경고 로그 │                      │
     │    └──────┬───────────┘                      │
     │           │                                   │
     └───────────┴───────────────────────────────────┘
```

#### 배치 수집 메커니즘

```
1. queue.get(timeout=3초) → 첫 아이템 수신
2. asyncio.sleep(1초)     → 추가 아이템 축적 대기
3. queue.get_nowait() 반복 → 큐에 있는 모든 아이템 수집
4. 배치 전체를 하나의 메시지로 포매팅하여 발송
```

#### 메시지 형식 (HTML)

```html
📰 <b>기사 제목</b>
---
리드 텍스트 (요약)
🔗 https://youtube.com/watch?v={video_id}

📰 <b>다음 기사 제목</b>
...
```

영상 하나가 시스템을 통과하는 전체 상태 전이를 보여준다.
`pipeline_status` 단일 컬럼으로 모든 단계를 추적한다.

```
   RSS Poller               Transcript Worker           LLM Worker            Notifier
   ─────────               ─────────────────           ──────────            ────────

   ┌─────────────┐
   │ videos      │
   │ INSERT      │
   │             │
   │ pipeline_   │
   │ status =    │
   │ 'transcript_│
   │  pending'   │
   └──────┬──────┘
          │
          ▼
                          ┌──────────────────┐
                          │ 자막 다운로드     │
                          │                  │
                          │ 성공 ──────────▶ pipeline_status = 'llm_pending'
                          │ 자막없음 ──────▶ pipeline_status = 'no_subtitle'       ← 종료
                          │ 실패 ──────────▶ pipeline_status = 'transcript_pending'
                          │                  + transcript_next_attempt_at 설정
                          │                  + transcript_retry_count++
                          └──────┬───────────┘
                                 │ (status='llm_pending' 경우)
                                 ▼
                                                    ┌──────────────────┐
                                                    │ LLM 기사화       │
                                                    │                  │
                                                    │ 시작 ──────────▶ pipeline_status = 'llm_processing'
                                                    │ 성공 ──────────▶ pipeline_status = 'done'
                                                    │                  + articles 테이블 INSERT
                                                    │ 실패 ──────────▶ pipeline_status = 'llm_failed'
                                                    │ (retry<3)        + retry_count++
                                                    │ 최종실패 ───────▶ pipeline_status = 'manual_review'
                                                    │ (retry>=3)
                                                    └──────┬───────────┘
                                                           │ (status='done' 경우)
                                                           ▼
                                                                           ┌────────────────┐
                                                                           │ Telegram 발송  │
                                                                           │                │
                                                                           │ notification_  │
                                                                           │ queue 소비     │
                                                                           │ → 배치 포매팅  │
                                                                           │ → 메시지 전송  │
                                                                           └────────────────┘
```

### Download Worker의 별도 상태 전이

## 6. 워커 활성화/비활성화

모든 워커는 `repository.is_worker_enabled(db, worker_name)` 호출로 활성화 상태를 확인한다.
`app_settings` 테이블에 `worker_{name}_enabled` 키로 저장되며, 기본값은 활성화(true)다.

비활성화 시 워커는 폴링을 중단하고 5초(Notifier는 3초) 간격으로 활성화 여부를 재확인한다.
이를 통해 운영 중 특정 워커를 일시 정지할 수 있다.

설정 API: `PUT /api/settings/workers`로 웹 UI에서 제어 가능.

## 7. 타이밍 메커니즘

### Monotonic Clock

Transcript Worker는 `time.monotonic()`를 사용하여 요청 간격을 측정한다.
시스템 시간 변경(NTP 동기화 등)에 영향받지 않는다.

```python
next_request_monotonic_at = time.monotonic() + jittered_interval
# ...
while time.monotonic() < next_request_monotonic_at:
    await asyncio.sleep(0.5)
```

### Jitter 계산

```python
base = request_interval_seconds × adaptive_factor
jitter_range = base × jitter_ratio  # ±30%
actual = base + random.uniform(-jitter_range, +jitter_range)
```

예시 (factor=2.0, 기본 15초):
- base = 30초
- jitter_range = ±9초
- actual = 21초 ~ 39초 사이의 랜덤 값

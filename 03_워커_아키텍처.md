# BriefTube 워커 아키텍처

> 4개의 비동기 워커가 YouTube 영상 수집 → 자막 추출 → LLM 기사화 → Telegram 알림의 파이프라인을 구성한다.

---

## 1. 전체 파이프라인 개요

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────┐     ┌──────────────┐
│  RSS Poller │────▶│ Transcript Worker│────▶│  LLM Worker │────▶│   Notifier   │
│  (poller.py)│     │(transcript_worker│     │(llm_worker. │     │(notifier_    │
│             │     │         .py)     │     │     py)     │     │  worker.py)  │
└─────────────┘     └──────────────────┘     └─────────────┘     └──────────────┘
      │                     │                       │                    │
      │  videos 테이블       │  transcripts 테이블    │  articles 테이블    │  notification
      │  INSERT             │  INSERT/UPDATE        │  INSERT/UPDATE    │  _queue 소비
      │  transcript_status  │  transcript_status    │  restructure_     │
      │  = 'pending'        │  = 'done'             │  status='done'    │
      ▼                     ▼                       ▼                    ▼
  ┌─────────────────────────────────────────────────────────────────────────┐
  │                         SQLite (WAL mode)                              │
  │  channels │ videos │ transcripts │ articles │ app_settings             │
  └─────────────────────────────────────────────────────────────────────────┘
```

### 워커 간 통신 채널

| 통신 방식 | 발신 | 수신 | 용도 |
|-----------|------|------|------|
| `videos` 테이블 상태 전이 | Poller → Transcript → LLM | 각 다음 단계 워커 | 파이프라인 체이닝 |
| `notification_queue` (asyncio.Queue) | LLM Worker | Notifier | 기사 완성 알림 |
| `poll_now_event` (asyncio.Event) | API 엔드포인트 | RSS Poller | 즉시 폴링 트리거 |
| `app_settings` KV 테이블 | Transcript Worker | Transcript Worker (재시작 시) | Guard 상태 영속화 |

## 2. 라이프사이클

`main.py`의 lifespan 컨텍스트 매니저에서 4개 워커를 동시에 생성하고, 앱 종료 시 일괄 취소한다.

```python
# main.py (lifespan)
tasks = [
    asyncio.create_task(run_rss_poller(runtime),       name="rss_poller"),
    asyncio.create_task(run_transcript_fetcher(runtime), name="transcript_fetcher"),
    asyncio.create_task(run_llm_queue_worker(runtime),  name="llm_queue_worker"),
    asyncio.create_task(run_telegram_notifier(runtime), name="telegram_notifier"),
]

# 종료 시
for t in tasks:
    t.cancel()
await asyncio.gather(*tasks, return_exceptions=True)
```

### 공유 상태 (AppState)

모든 워커는 `AppState` 인스턴스를 통해 공유 자원에 접근한다.

```
AppState
├── config           # AppConfig (설정값)
├── db               # aiosqlite.Connection
├── http_client      # httpx.AsyncClient
├── rss_service      # RSSService
├── transcript_service # TranscriptService
├── channel_resolver # ChannelResolverService
├── llm_client       # OpenClawClient
├── telegram_notifier # TelegramNotifier
├── poll_now_event   # asyncio.Event
├── notification_queue # asyncio.Queue[dict]
└── rss_cache        # dict (ETag/Last-Modified)
```

## 3. 워커별 상세 흐름

### 3.1 RSS Poller (`poller.py`)

YouTube RSS 피드를 주기적으로 폴링하여 새 영상을 `videos` 테이블에 삽입한다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   비활성화
          │ 워커 활성화?  │─────────▶ 5초 대기 후 재확인
          └──────┬───────┘
                 │ 활성화
                 ▼
     ┌───────────────────────┐
     │ 대기 (polling_interval)│◀──────────────────────────┐
     │  * 5초 단위 체크       │                           │
     │  * poll_now_event 감시 │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │    poll_once() 실행    │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │ 활성 채널 목록 조회    │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │   채널별 RSS 피드 요청  │                           │
     │  (ETag/Last-Modified  │                           │
     │   캐시 활용)           │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  304 Not Modified?    │──── YES ──▶ 다음 채널 ────┤
     └───────────┬───────────┘                           │
                 │ NO                                     │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  404 Not Found?       │──── YES ──▶ 채널 비활성화 ─┤
     └───────────┬───────────┘            + 시스템 알림   │
                 │ NO                                     │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  Watermark 이후 영상   │                           │
     │  필터링 + DB INSERT    │                           │
     │  (insert_video_if_    │                           │
     │   absent)              │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  채널 Watermark 갱신   │───────────────────────────┘
     └───────────────────────┘
```

#### 핵심 동작

| 항목 | 값 | 설명 |
|------|-----|------|
| 폴링 간격 | `polling_interval_minutes` (기본 15분) | 최소 60초 보장 |
| Watermark | `channels.last_seen_published_at` | 채널별로 마지막 확인 시점 기록 |
| Lookback | `rss_bootstrap_lookback_days` (기본 60일) | 신규 채널 첫 폴링 시 과거 범위 |
| 즉시 트리거 | `poll_now_event` | API에서 설정하면 대기 중단, 즉시 폴링 |
| 캐시 | `rss_cache` (ETag, Last-Modified) | 304 응답으로 불필요한 처리 방지 |

#### DB 상호작용

- **읽기**: `channels` (is_active=1), `app_settings` (rss_bootstrap_lookback_days)
- **쓰기**: `videos` (INSERT, transcript_status='pending'), `channels` (watermark 갱신)

YouTube API의 429/403 응답에 대응하는 **적응형 가드 메커니즘**이 핵심이다.

     │           │ 활성화
     │           ▼

#### Transcript Guard 상태 머신

가드는 YouTube의 응답에 따라 요청 속도를 동적으로 조절한다.

```
                        ┌──────────────────────┐
                        │    정상 상태          │
                        │  adaptive_factor=1.0 │
                        │  간격 ≈ 15초          │
                        └──────┬──────┬────────┘
                               │      │
                    429/403 발생│      │일반 에러 발생
                               │      │
                               ▼      ▼
              ┌────────────────────┐ ┌─────────────────┐
              │  하드 쓰로틀 상태   │ │  소프트 저하 상태 │
              │  factor ×2.0      │ │  factor ×1.25   │
              │  + 하드 쿨다운     │ │                 │
              │  (300s~3600s)     │ │                 │
              └────────┬─────────┘ └────────┬────────┘
                       │                     │
                       │  5회 연속 성공        │  5회 연속 성공
                       │                     │
                       ▼                     ▼
              ┌────────────────────────────────────────┐
              │           복구 단계                     │
              │  factor ×0.8 (5회 연속 성공마다)         │
              │  점진적으로 1.0으로 복귀                  │
              └────────────────────────────────────────┘
```

#### Guard 수치 시뮬레이션

**하드 쓰로틀 악화 경로** (연속 429/403):

| 발생 횟수 | adaptive_factor | 요청 간격 (기본 15s) | 쿨다운 시간 |
|-----------|-----------------|---------------------|------------|
| 초기 | 1.0 | ~15초 | - |
| 1회 | 2.0 | ~30초 | 5분 (300s) |
| 2회 | 4.0 | ~60초 | 10분 (600s) |
| 3회 | 8.0 (상한) | ~120초 | 20분 (1200s) |
| 4회+ | 8.0 (고정) | ~120초 | 60분 (3600s, 상한) |

**복구 경로** (factor=8.0에서 연속 성공):

| 복구 라운드 | 연속 성공 | adaptive_factor | 요청 간격 |
|------------|----------|-----------------|----------|
| 시작 | 0 | 8.0 | ~120초 |
| 1차 복구 | 5회 | 6.4 | ~96초 |
| 2차 복구 | 10회 | 5.12 | ~77초 |
| 3차 복구 | 15회 | 4.10 | ~61초 |
| ... | ... | ... | ... |
| n차 복구 | 5n회 | 8.0 × 0.8^n | 점진 감소 |

> 모든 간격에는 ±30% 지터가 적용되어 요청 패턴이 분산된다.

#### 자막 재시도 지수 백오프

```
delay = min(base × 2^retry_count, max_delay)
```

| 재시도 횟수 | 지연 시간 | 비고 |
|------------|----------|------|
| 0 | 120초 (2분) | 첫 실패 |
| 1 | 240초 (4분) | |
| 2 | 480초 (8분) | |
| 3 | 960초 (16분) | |
| 4 | 1920초 (32분) | |
| 5+ | 3600초 (1시간) | 상한 고정 |

#### 오류 분류 기준

| 분류 | 판정 조건 | 처리 |
|------|----------|------|
| **자막 없음** | 메시지에 "transcript is disabled", "not available", "no transcript", "could not retrieve" 포함 | `no_subtitle` 마킹, 재시도 없음 |
| **하드 쓰로틀** | HTTP 429/403, 또는 메시지에 "forbidden", "too many requests", "rate limit", "quota" 포함 | factor ×2, 하드 쿨다운 활성화 |
| **일반 에러** | 위에 해당하지 않는 모든 예외 | factor ×1.25, 일반 재시도 |

#### DB 상호작용

- **읽기**: `videos` (transcript_status='pending', next_attempt_at 조건), `app_settings` (guard 상태)
- **쓰기**: `transcripts` (INSERT/UPDATE), `videos` (상태/재시도 갱신), `app_settings` (guard 상태 저장)

### 3.3 LLM Worker (`llm_worker.py`)

자막이 완료된 영상(`transcript_status='done'`)을 LLM으로 기사 형식으로 재구성한다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   비활성화
     ┌───▶│ 워커 활성화?  │─────────▶ 5초 대기 후 재확인
     │    └──────┬───────┘
     │           │ 활성화
     │           ▼
     │    ┌──────────────────┐   없음
     │    │ LLM 후보 조회    │─────────▶ 5초 대기 ──┐
     │    │ (transcript_     │                      │
     │    │  status='done'   │                      │
     │    │  + restructure_  │                      │
     │    │  status IN       │                      │
     │    │  ('pending',     │                      │
     │    │   'failed'))     │                      │
     │    └──────┬───────────┘                      │
     │           │ 있음                              │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ restructure_     │                      │
     │    │ status =         │                      │
     │    │ 'processing'     │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ LLM restructure  │                      │
     │    │ (title, lead,    │                      │
     │    │  body, fact_box, │                      │
     │    │  timestamps)     │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │     성공?        │                      │
     │    └──┬──────────┬───┘                      │
     │       │ YES      │ NO                        │
     │       ▼          ▼                           │
     │  ┌─────────┐ ┌───────────────┐              │
     │  │기사 저장 │ │ retry_count   │              │
     │  │status=  │ │ < 3?          │              │
     │  │ 'done'  │ │  YES → failed │              │
     │  │         │ │  NO  → manual │              │
     │  │알림 큐에│ │       _review │              │
     │  │추가     │ └───────┬───────┘              │
     │  └────┬────┘         │                       │
     │       │              │                       │
     └───────┴──────────────┴───────────────────────┘
```

#### 상태 전이

```
pending ──▶ processing ──▶ done           (성공)
                      └──▶ failed         (실패, retry_count < 3)
failed  ──▶ processing ──▶ done           (재시도 성공)
                      └──▶ failed         (재실패, retry_count < 3)
                      └──▶ manual_review  (retry_count >= 3, 최종 실패)
```

#### LLM 출력 구조

```json
{
  "title":      "기사 제목",
  "lead":       "리드 문단 (요약)",
  "body":       "본문",
  "fact_box":   "팩트박스 (선택)",
  "timestamps": "타임스탬프 (선택)"
}
```

#### DB 상호작용

- **읽기**: `videos` + `transcripts` (JOIN, 후보 조회)
- **쓰기**: `articles` (INSERT/UPDATE), `videos` (restructure_status, retry_count)
- **큐**: 성공 시 `notification_queue.put()` → Notifier로 전달

### 3.4 Telegram Notifier (`notifier_worker.py`)

LLM 워커가 큐에 넣은 완성 기사를 Telegram으로 배치 발송한다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   미설정
     ┌───▶│ TG 설정 확인  │─────────▶ 5초 대기 후 재확인
     │    │ (토큰+채팅ID) │
     │    └──────┬───────┘
     │           │ 설정됨
     │           ▼
     │    ┌──────────────┐   비활성화
     │    │ 워커 활성화?  │─────────▶ 3초 대기 후 재확인
     │    └──────┬───────┘
     │           │ 활성화
     │           ▼
     │    ┌──────────────────┐   타임아웃 (3초)
     │    │ 큐에서 아이템 대기│─────────▶ continue ──┐
     │    │ (timeout=3초)    │                      │
     │    └──────┬───────────┘                      │
     │           │ 아이템 수신                        │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 1초 대기 후       │                      │
     │    │ 추가 아이템 수집  │                      │
     │    │ (get_nowait 반복) │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 배치 메시지 포매팅│                      │
     │    │ (HTML 형식)      │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ Telegram 발송    │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 응답 확인        │                      │
     │    │ 실패 시 경고 로그 │                      │
     │    └──────┬───────────┘                      │
     │           │                                   │
     └───────────┴───────────────────────────────────┘
```

#### 배치 수집 메커니즘

```
1. queue.get(timeout=3초) → 첫 아이템 수신
2. asyncio.sleep(1초)     → 추가 아이템 축적 대기
3. queue.get_nowait() 반복 → 큐에 있는 모든 아이템 수집
4. 배치 전체를 하나의 메시지로 포매팅하여 발송
```

#### 메시지 형식 (HTML)

```html
📰 <b>기사 제목</b>
---
리드 텍스트 (요약)
🔗 https://youtube.com/watch?v={video_id}

📰 <b>다음 기사 제목</b>
...
```

## 6. 워커 활성화/비활성화

모든 워커는 `repository.is_worker_enabled(db, worker_name)` 호출로 활성화 상태를 확인한다.
`app_settings` 테이블에 `worker_{name}_enabled` 키로 저장되며, 기본값은 활성화(true)다.

비활성화 시 워커는 폴링을 중단하고 5초(Notifier는 3초) 간격으로 활성화 여부를 재확인한다.
이를 통해 운영 중 특정 워커를 일시 정지할 수 있다.

## 7. 타이밍 메커니즘

### Monotonic Clock

Transcript Worker는 `time.monotonic()`를 사용하여 요청 간격을 측정한다.
시스템 시간 변경(NTP 동기화 등)에 영향받지 않는다.

```python
next_request_monotonic_at = time.monotonic() + jittered_interval
# ...
while time.monotonic() < next_request_monotonic_at:
    await asyncio.sleep(0.5)
```

### Jitter 계산

```python
base = request_interval_seconds × adaptive_factor
jitter_range = base × jitter_ratio  # ±30%
actual = base + random.uniform(-jitter_range, +jitter_range)
```

예시 (factor=2.0, 기본 15초):
- base = 30초
- jitter_range = ±9초
- actual = 21초 ~ 39초 사이의 랜덤 값

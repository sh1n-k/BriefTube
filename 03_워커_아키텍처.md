# BriefTube 워커 아키텍처

> 5개의 비동기 워커가 YouTube 영상 수집 → 자막 추출 → LLM 기사화 → Telegram 알림 + 영상 다운로드 파이프라인을 구성한다.

---

## 1. 전체 파이프라인 개요

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────┐     ┌──────────────┐
│  RSS Poller │────▶│ Transcript Worker│────▶│  LLM Worker │────▶│   Notifier   │
│  (poller.py)│     │(transcript_worker│     │(llm_worker. │     │(notifier_    │
│             │     │         .py)     │     │     py)     │     │  worker.py)  │
└─────────────┘     └──────────────────┘     └─────────────┘     └──────────────┘
      │                     │                       │                    │
      │  videos 테이블       │  transcripts 테이블    │  articles 테이블    │  notification
      │  INSERT             │  INSERT/UPDATE        │  INSERT/UPDATE    │  _queue 소비
      │  pipeline_status    │  pipeline_status      │  pipeline_status  │
      │  = 'transcript_     │  = 'llm_pending'      │  = 'done'         │
      │     pending'        │                       │                    │
      ▼                     ▼                       ▼                    ▼
  ┌─────────────────────────────────────────────────────────────────────────┐
  │                         SQLite (WAL mode)                              │
  │  channels │ videos │ transcripts │ articles │ app_settings             │
  │  system_alerts │ download_jobs │ download_events                       │
  └─────────────────────────────────────────────────────────────────────────┘
                                      ▲
                                      │
                             ┌────────┴────────┐
                             │ Download Worker  │
                             │(download_worker  │
                             │         .py)     │
                             └─────────────────┘
                               download_jobs
                               테이블 소비
```

### 워커 간 통신 채널

| 통신 방식 | 발신 | 수신 | 용도 |
|-----------|------|------|------|
| `videos` 테이블 상태 전이 | Poller → Transcript → LLM | 각 다음 단계 워커 | 파이프라인 체이닝 |
| `notification_queue` (asyncio.Queue) | LLM Worker | Notifier | 기사 완성 알림 |
| `poll_now_event` (asyncio.Event) | API 엔드포인트 | RSS Poller | 즉시 폴링 트리거 |
| `download_wake_event` (asyncio.Event) | API 엔드포인트 | Download Worker | 새 다운로드 즉시 시작 |
| `app_settings` KV 테이블 | Transcript Worker | Transcript Worker (재시작 시) | Guard 상태 영속화 |
| `system_alerts` 테이블 | RSS Poller | 웹 UI (토스트) | 채널 404 등 운영 이벤트 |

## 2. 라이프사이클

`main.py`의 lifespan 컨텍스트 매니저에서 5개 워커를 동시에 생성하고, 앱 종료 시 일괄 취소한다.

```python
# main.py (lifespan)
tasks = [
    asyncio.create_task(run_rss_poller(runtime),        name="rss_poller"),
    asyncio.create_task(run_download_worker(runtime),    name="download_worker"),
    asyncio.create_task(run_transcript_fetcher(runtime), name="transcript_fetcher"),
    asyncio.create_task(run_llm_queue_worker(runtime),   name="llm_queue_worker"),
    asyncio.create_task(run_telegram_notifier(runtime),  name="telegram_notifier"),
]

# 종료 시
for t in tasks:
    t.cancel()
await asyncio.gather(*tasks, return_exceptions=True)
await http_client.aclose()
await db.close()
```

### 공유 상태 (AppState)

모든 워커는 `AppState` 인스턴스를 통해 공유 자원에 접근한다.

```
AppState
├── config              # AppConfig (설정값)
├── db                  # aiosqlite.Connection
├── http_client         # httpx.AsyncClient
├── rss_service         # RSSService
├── transcript_service  # TranscriptService
├── channel_resolver    # ChannelResolverService
├── llm_client          # UnifiedLlmClient
├── telegram_notifier   # TelegramNotifier
├── started_at          # datetime (앱 시작 시각)
├── poll_now_event      # asyncio.Event (즉시 RSS 폴링)
├── download_wake_event # asyncio.Event (다운로드 깨우기)
├── notification_queue  # asyncio.Queue[dict] (텔레그램 알림)
└── rss_cache           # dict (ETag/Last-Modified)
```

## 3. 워커별 상세 흐름

### 3.1 RSS Poller (`poller.py`)

> **쉬운 설명**: 구독한 YouTube 채널들의 "새 영상 목록"을 주기적으로 확인하는 워커다.
> 마치 우체부가 정해진 시간마다 우편함을 확인하듯, 15분마다 각 채널의 RSS 피드를 방문해서 새 영상이 올라왔는지 살펴본다.
> 새 영상을 발견하면 DB에 등록해서 다음 워커(Transcript Worker)가 처리할 수 있게 한다.
> 만약 채널이 삭제되어 404 에러가 나면, 자동으로 채널을 비활성화하고 관리자에게 알림을 보낸다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   비활성화
          │ 워커 활성화?  │─────────▶ 5초 대기 후 재확인
          └──────┬───────┘
                 │ 활성화
                 ▼
     ┌───────────────────────┐
     │ 대기 (polling_interval)│◀──────────────────────────┐
     │  * 5초 단위 체크       │                           │
     │  * poll_now_event 감시 │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │    poll_once() 실행    │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │ 활성 채널 목록 조회    │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │   채널별 RSS 피드 요청  │                           │
     │  (ETag/Last-Modified  │                           │
     │   캐시 활용)           │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  304 Not Modified?    │──── YES ──▶ 다음 채널 ────┤
     └───────────┬───────────┘                           │
                 │ NO                                     │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  404 Not Found?       │──── YES ──▶ 채널 비활성화 ─┤
     └───────────┬───────────┘            + 시스템 알림   │
                 │ NO                                     │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  Watermark 이후 영상   │                           │
     │  필터링 + DB INSERT    │                           │
     │  (insert_video_if_    │                           │
     │   absent)              │                           │
     └───────────┬───────────┘                           │
                 ▼                                        │
     ┌───────────────────────┐                           │
     │  채널 Watermark 갱신   │───────────────────────────┘
     └───────────────────────┘
```

#### 핵심 동작

| 항목 | 값 | 설명 |
|------|-----|------|
| 폴링 간격 | `polling_interval_minutes` (기본 15분) | 최소 60초 보장 |
| Watermark | `channels.last_seen_published_at` | 채널별로 마지막 확인 시점 기록 |
| Lookback | `rss_bootstrap_lookback_days` (기본 60일) | 신규 채널 첫 폴링 시 과거 범위 |
| 즉시 트리거 | `poll_now_event` | API에서 설정하면 대기 중단, 즉시 폴링 |
| 캐시 | `rss_cache` (ETag, Last-Modified) | 304 응답으로 불필요한 처리 방지 |
| 404 처리 | 채널 자동 비활성화 | `system_alerts`에 알림 생성 |

#### DB 상호작용

- **읽기**: `channels` (is_active=1), `app_settings` (rss_bootstrap_lookback_days)
- **쓰기**: `videos` (INSERT, pipeline_status='transcript_pending'), `channels` (watermark 갱신), `system_alerts` (404 시 INSERT)

### 3.2 Transcript Worker (`transcript_worker.py`)

> **쉬운 설명**: YouTube 영상의 자막(대본)을 가져오는 워커다.
> RSS Poller가 새 영상을 등록하면, 이 워커가 YouTube에서 자막 텍스트를 다운로드한다.
> 하지만 YouTube에 너무 빠르게 요청하면 차단당할 수 있기 때문에, "교통 신호등" 같은 보호 장치(Transcript Guard)가 있다.
> 요청이 거부(429/403)되면 자동으로 속도를 늦추고, 문제가 풀리면 다시 속도를 올린다.
> 또한 같은 채널에 연달아 요청하지 않도록 채널별로 쿨다운 간격을 둔다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
     ┌───────────────────────┐
     │  Guard 상태 로드       │  ◀── app_settings KV 테이블
     │  (adaptive_factor,    │
     │   cooldown_until 등)  │
     └───────────┬───────────┘
                 ▼
          ┌──────────────┐   비활성화
     ┌───▶│ 워커 활성화?  │─────────▶ 5초 대기 후 재확인
     │    └──────┬───────┘
     │           │ 활성화
     │           ▼
     │    ┌──────────────────┐   쿨다운 중
     │    │ 쿨다운 체크       │─────────▶ 남은 시간 대기
     │    │ (cooldown_until) │           쿨다운 해제 시 상태 초기화
```

#### Transcript Guard 상태 머신

가드는 YouTube의 응답에 따라 요청 속도를 동적으로 조절한다.

```
                        ┌──────────────────────┐
                        │    정상 상태          │
                        │  adaptive_factor=1.0 │
                        │  간격 ≈ 15초          │
                        └──────┬──────┬────────┘
                               │      │
                    429/403 발생│      │일반 에러 발생
                               │      │
                               ▼      ▼
              ┌────────────────────┐ ┌─────────────────┐
              │  하드 쓰로틀 상태   │ │  소프트 저하 상태 │
              │  factor ×2.0      │ │  factor ×1.25   │
              │  + 하드 쿨다운     │ │                 │
              │  (300s~3600s)     │ │                 │
              └────────┬─────────┘ └────────┬────────┘
                       │                     │
                       │  5회 연속 성공        │  5회 연속 성공
                       │                     │
                       ▼                     ▼
              ┌────────────────────────────────────────┐
              │           복구 단계                     │
              │  factor ×0.8 (5회 연속 성공마다)         │
              │  점진적으로 1.0으로 복귀                  │
              └────────────────────────────────────────┘
```

#### Guard 수치 시뮬레이션

**하드 쓰로틀 악화 경로** (연속 429/403):

| 발생 횟수 | adaptive_factor | 요청 간격 (기본 15s) | 쿨다운 시간 |
|-----------|-----------------|---------------------|------------|
| 초기 | 1.0 | ~15초 | - |
| 1회 | 2.0 | ~30초 | 5분 (300s) |
| 2회 | 4.0 | ~60초 | 10분 (600s) |
| 3회 | 8.0 (상한) | ~120초 | 20분 (1200s) |
| 4회+ | 8.0 (고정) | ~120초 | 60분 (3600s, 상한) |

**복구 경로** (factor=8.0에서 연속 성공):

| 복구 라운드 | 연속 성공 | adaptive_factor | 요청 간격 |
|------------|----------|-----------------|----------|
| 시작 | 0 | 8.0 | ~120초 |
| 1차 복구 | 5회 | 6.4 | ~96초 |
| 2차 복구 | 10회 | 5.12 | ~77초 |
| 3차 복구 | 15회 | 4.10 | ~61초 |
| ... | ... | ... | ... |
| n차 복구 | 5n회 | 8.0 × 0.8^n | 점진 감소 |

> 모든 간격에는 ±30% 지터가 적용되어 요청 패턴이 분산된다.

#### 자막 재시도 지수 백오프

```
delay = min(base × 2^retry_count, max_delay)
```

| 재시도 횟수 | 지연 시간 | 비고 |
|------------|----------|------|
| 0 | 120초 (2분) | 첫 실패 |
| 1 | 240초 (4분) | |
| 2 | 480초 (8분) | |
| 3 | 960초 (16분) | |
| 4 | 1920초 (32분) | |
| 5+ | 3600초 (1시간) | 상한 고정 |

최대 재시도 횟수: `transcript_retry_max_attempts` (기본 8회)

#### 오류 분류 기준

| 분류 | 판정 조건 | 처리 |
|------|----------|------|
| **자막 없음** | 메시지에 "transcript is disabled", "not available", "no transcript", "could not retrieve" 포함 | `no_subtitle` 마킹, 재시도 없음 |
| **하드 쓰로틀** | HTTP 429/403, 또는 메시지에 "forbidden", "too many requests", "rate limit", "quota" 포함 | factor ×2, 하드 쿨다운 활성화 |
| **일반 에러** | 위에 해당하지 않는 모든 예외 | factor ×1.25, 일반 재시도 |

#### DB 상호작용

- **읽기**: `videos` (pipeline_status='transcript_pending', transcript_next_attempt_at 조건), `app_settings` (guard 상태)
- **쓰기**: `transcripts` (INSERT/UPDATE), `videos` (상태/재시도 갱신), `app_settings` (guard 상태 저장)

### 3.3 LLM Worker (`llm_worker.py`)

> **쉬운 설명**: 자막 텍스트를 읽기 좋은 "뉴스 기사"로 변환하는 워커다.
> Transcript Worker가 자막을 저장하면, 이 워커가 AI(LLM)에게 "이 자막을 기사 형태로 정리해줘"라고 요청한다.
> AI가 제목·요약·본문·팩트박스·타임스탬프를 만들어 돌려주면 DB에 저장한다.
> 만약 AI 호출이 실패하면 최대 3번까지 자동 재시도하고, 3번 다 실패하면 "사람이 확인 필요" 상태로 표시한다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   비활성화
     ┌───▶│ 워커 활성화?  │─────────▶ 5초 대기 후 재확인
     │    └──────┬───────┘
     │           │ 활성화
     │           ▼
     │    ┌──────────────────┐   없음
     │    │ LLM 후보 조회    │─────────▶ 5초 대기 ──┐
     │    │ (pipeline_status │                      │
     │    │  IN ('llm_      │                      │
     │    │  pending',      │                      │
     │    │  'llm_failed')) │                      │
     │    └──────┬───────────┘                      │
     │           │ 있음                              │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ pipeline_status  │                      │
     │    │ = 'llm_         │                      │
     │    │   processing'   │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ LLM restructure  │                      │
     │    │ (title, lead,    │                      │
     │    │  body, fact_box, │                      │
     │    │  timestamps)     │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │     성공?        │                      │
     │    └──┬──────────┬───┘                      │
     │       │ YES      │ NO                        │
     │       ▼          ▼                           │
     │  ┌─────────┐ ┌───────────────┐              │
     │  │기사 저장 │ │ retry_count   │              │
     │  │pipeline_ │ │ < 3?          │              │
```

### 3.4 Download Worker (`download_worker.py`)

> **쉬운 설명**: YouTube 영상 파일(mp4)을 컴퓨터에 저장하는 워커다.
> 사용자가 웹 UI에서 "다운로드" 버튼을 누르면, `download_jobs` 테이블에 작업이 등록된다.
> 이 워커는 등록된 작업을 하나씩 꺼내서 yt-dlp 프로그램을 실행해 영상을 다운로드한다.
> 동시에 최대 2~3개까지 병렬로 다운로드할 수 있고, 완료되면 파일 경로와 크기를 기록한다.
> 다운로드 중 에러가 나면 원인(ffmpeg 없음, 403 차단, 타임아웃 등)을 분류해서 저장한다.

### 3.5 Telegram Notifier (`notifier_worker.py`)

> **쉬운 설명**: LLM이 만든 기사를 Telegram 메신저로 알려주는 워커다.
> LLM Worker가 기사를 완성하면 "알림 대기줄"(Queue)에 넣는다.
> 이 워커는 대기줄을 지켜보다가, 기사가 도착하면 1초 정도 기다려서 여러 건을 모은 뒤
> 하나의 Telegram 메시지로 묶어서 보낸다.
> Telegram 설정(토큰, 채팅 ID)이 없으면 자동으로 대기 상태가 된다.

#### 흐름도

```
          ┌──────────────┐
          │   워커 시작    │
          └──────┬───────┘
                 ▼
          ┌──────────────┐   미설정
     ┌───▶│ TG 설정 확인  │─────────▶ 5초 대기 후 재확인
     │    │ (토큰+채팅ID) │
     │    └──────┬───────┘
     │           │ 설정됨
     │           ▼
     │    ┌──────────────┐   비활성화
     │    │ 워커 활성화?  │─────────▶ 3초 대기 후 재확인
     │    └──────┬───────┘
     │           │ 활성화
     │           ▼
     │    ┌──────────────────┐   타임아웃 (3초)
     │    │ 큐에서 아이템 대기│─────────▶ continue ──┐
     │    │ (timeout=3초)    │                      │
     │    └──────┬───────────┘                      │
     │           │ 아이템 수신                        │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 1초 대기 후       │                      │
     │    │ 추가 아이템 수집  │                      │
     │    │ (get_nowait 반복) │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 배치 메시지 포매팅│                      │
     │    │ (HTML 형식)      │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ Telegram 발송    │                      │
     │    └──────┬───────────┘                      │
     │           ▼                                   │
     │    ┌──────────────────┐                      │
     │    │ 응답 확인        │                      │
     │    │ 실패 시 경고 로그 │                      │
     │    └──────┬───────────┘                      │
     │           │                                   │
     └───────────┴───────────────────────────────────┘
```

#### 배치 수집 메커니즘

```
1. queue.get(timeout=3초) → 첫 아이템 수신
2. asyncio.sleep(1초)     → 추가 아이템 축적 대기
3. queue.get_nowait() 반복 → 큐에 있는 모든 아이템 수집
4. 배치 전체를 하나의 메시지로 포매팅하여 발송
```

#### 메시지 형식 (HTML)

```html
📰 <b>기사 제목</b>
---
리드 텍스트 (요약)
🔗 https://youtube.com/watch?v={video_id}

📰 <b>다음 기사 제목</b>
...
```

```
   RSS Poller               Transcript Worker           LLM Worker            Notifier
   ─────────               ─────────────────           ──────────            ────────

          │
          ▼
                          ┌──────────────────┐
                          │ 자막 다운로드     │
                          │                  │
                          │ 성공 ──────────▶ pipeline_status = 'llm_pending'
                          │ 자막없음 ──────▶ pipeline_status = 'no_subtitle'       ← 종료
                          │ 실패 ──────────▶ pipeline_status = 'transcript_pending'

                          └──────┬───────────┘

                                                    ┌──────────────────┐
                                                    │ LLM 기사화       │

                                                    │ 시작 ──────────▶ pipeline_status = 'llm_processing'
                                                    │ 성공 ──────────▶ pipeline_status = 'done'

                                                    │ 실패 ──────────▶ pipeline_status = 'llm_failed'
```

## 7. 타이밍 메커니즘

### Monotonic Clock

Transcript Worker는 `time.monotonic()`를 사용하여 요청 간격을 측정한다.
시스템 시간 변경(NTP 동기화 등)에 영향받지 않는다.

```python
next_request_monotonic_at = time.monotonic() + jittered_interval
# ...
while time.monotonic() < next_request_monotonic_at:
    await asyncio.sleep(0.5)
```

### Jitter 계산

```python
base = request_interval_seconds × adaptive_factor
jitter_range = base × jitter_ratio  # ±30%
actual = base + random.uniform(-jitter_range, +jitter_range)
```

예시 (factor=2.0, 기본 15초):
- base = 30초
- jitter_range = ±9초
- actual = 21초 ~ 39초 사이의 랜덤 값
